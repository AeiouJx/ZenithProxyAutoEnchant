## 1. 项目概述

### 1.1 背景

Minecraft Java 版中，把一件装备堆到「最佳附魔」（如头盔 45 级、护腿 44 级）需要按特定顺序合并附魔书与装备。合并顺序错误会显著抬高铁砧的先前工作惩罚（prior work penalty），最终触发「过于昂贵」上限而无法完成。中文 Wiki 的《最佳附魔指南》给出了每种装备槽位的低经验合并树，但人工执行成本高、易出错，且需要反复开关箱子、铁砧、砂轮并刷经验。

### 1.2 目标

为 ZenithProxy 无头 BOT 提供**可长期无人值守运行**的自动附魔能力：

1. 自动发现/绑定铁砧、砂轮与标记容器；
2. 从输入容器取待处理装备，按内置版本化预设或自定义方案生成附魔计划；
3. 按低经验合并树逐步执行铁砧合并，每一步以服务端窗口预览为准校验费用与结果；
4. 经验不足时通过本体 `KillAura` 刷取；
5. 成品卸货、半成品隔离、失败恢复，任何单件异常都不阻塞队列。

### 1.3 系统定位

本插件是 ZenithProxy 的**进程内插件**（非独立服务、非 Fabric/Forge Mod），通过 ZenithProxy 提供的 Module / Command / Inventory / Pathing / Packet 拦截 API 与游戏交互。BOT 本身无渲染、无真实客户端，所有状态来自代理侧的 packet cache（`CACHE`）。

### 1.4 术语表

| 术语 | 含义 |
| --- | --- |
| 预设（Preset） | 与装备槽位绑定、与材质解耦的附魔方案，如 `helmet.all`、`sword.no_fire_knockback` |
| 合并树表达式 | Wiki 给出的 `{(a + b)@c + d}@e` 形式的组合表达式，`@n` 为该次合并的指南费用 |
| 白板装备 | 无任何附魔的装备；PRESET 方案的前提条件 |
| 先前工作惩罚 | 物品的 `minecraft:repair_cost` 组件（1.21+），铁砧费用的主要放大因子 |
| 事务（Transaction） | 从输入容器取出一件装备，到该装备卸货/丢弃的完整生命周期 |
| 标记（Marker） | 展示框内物品 → 容器角色 的绑定约定（红石粉/红石块/铁砧/附魔书/灰色染料） |
| 单件串行 | 同一时刻只允许一个事务存在，禁止并发处理多件装备 |

### 2.3 已实现能力

| 能力 | 实现位置 | 说明 |
| --- | --- | --- |
| 配置注册与持久化 | `Plugin.onLoad` | `plugins/config/auto-enchant.json` |
| 预设加载与版本校验 | `Catalog.load` | `dataVersion` 与构建 MC 版本不一致即拒绝加载 |
| 表达式解析与自检 | `Parser` + `Catalog.annotatedCost` | 解析出的 `@cost` 累加值必须等于 `totalLevels`，否则拒绝该预设 |
| 铁砧/砂轮发现 | `Module.scanNow` | 半径内三重循环扫描 + 显式坐标优先 |
| 展示框识别 | `Module.markerRole` / `Module.jobFrame` | 带耐久物品→作业（物品 + 取货箱 + 上方红石灯启停）；铁砧→铁砧补给、附魔书→按附魔+等级的书箱、灰染料→半成品；红石粉/红石块仍作为全局兜底 |
| 作业匹配 | `Module.jobFor` | 按 `jobs[]` 中启用的条目比对物品 id，命中即绑定该条目 |
| 计划生成（PRESET） | `Worker.preparePlan` | 扁平化合并树为操作序列 + 书需求列表 |
| 计划生成（CUSTOM） | `Worker.preparePlan` | 线性链：装备依次与每本书合并 |
| 砂轮祛魔 | `Worker.decideOnHandoff` | 取件时一次性判定：白板不洗、PRESET 有附魔洗一次、已达标原样卸货；`prepareGrindstone` 硬校验来源必须是取货箱 |
| 半成品续做 | `Worker.applyResumePlan` + `Catalog.resumePlan` + `CustomEnchantPlanner.plan` | PRESET 按优化树对齐：背包中已存在的子树产物直接复用，只构建缺失分支，无法对齐即卸货；CUSTOM 用费用模型从当前附魔与真实惩罚重新规划最优合并树 |
| 部分附魔续做 | `Worker.applyResumePlan` | 已有附魔作为首个合并的左值，只补缺失的书；已完成则不重复操作直接卸货 |
| 铁砧补给 | `CHECK_ANVIL` / `OPEN_SUPPLY` / `PLACE_ANVIL` | 铁砧消失→查背包→不足则从 `anvil_supply` 取 N 组→原位置放置 |
| 铁砧合并 | `PLACE_INPUTS` → `WAIT_PREVIEW` | 服务端费用预览 + 结果附魔比对，`> 39` 拒绝 |
| XP 联动 | `Module.ensureXpForCost` 等 | 关闭窗口→开 KillAura→达阈值→继续；含死亡/传送/换维度/超时中断 |
| 卸货与失败处理 | `PREPARE_OUTPUT` / `DROP_ITEM` / `BACKOFF` | 成品→输出箱；失败→半成品箱→输出箱→丢弃 |
| 单向防重复点击 | `InventoryActionRequest` + `deadline` + 窗口 ID 校验 | 提交后等待 future 完成才推进状态 |
| 调试可观测 | `debugSnapshot` | BOT 位姿、附近容器、每个展示框的显示物/角色/附着方块/是否接受 |

### 2.4 设计与实现差距（关键）

> 下表是本文档最重要的部分：`design.md` 已明确要求、但代码未实现或仅部分实现的能力。迭代排期以此为输入。

| ID | design.md 要求 | 代码现状 | 影响 |
| --- | --- | --- | --- |
| G-01 | §9 铁砧损坏检测与从 `anvilChest` 补货 | 仅识别 `anvil_supply` 标记角色；`containerPosition("anvil_supply")` **从未被调用**；无铁砧方块状态复核、无放置逻辑 | 铁砧耗尽即整条产线停摆 |
| G-02 | §11 三级错误分类 item-skip / transient-retry / configuration-error | 所有失败统一走 `failureReason` 单字符串 + 固定 `failureReason != null ? 半成品 : 成品` 二分 | 无法区分「该跳件」与「该退避重试」 |
| G-03 | §6.1 有上限的指数退避 | `BACKOFF` 仅等待 `restartDelayMs` 后 `reset()` 回 IDLE | 书箱空/容器满时会以固定周期反复取件—失败—卸货，持续消耗耗材 |

| G-08 | §2 手动绑定 `ae bind <role>`、`ae reload`、`ae status`；命令前缀 `ae` | 命令为 `autoEnchant`，无 bind/reload/status 子命令；热重载只在模块 `onEnable` 时发生 | 现场调试只能改配置文件 + 重启代理 |
| G-09 | §2 标记解析需校验附着面、偏移、容器类型、**可访问性**与**重复绑定** | 已校验附着面、偏移、容器类型、区块加载；重复绑定与「期望位置不是容器」仅在日志/`stations` 中上报，尚未自动择一绑定 | 现场多贴一个展示框会跳过该角色，但原因可见（FR-2.7 仍待做） |
| G-10 | §10 `dryRun: true` 输出匹配目标、解析表达式、预计费用与材料清单 | `tick()` 在 dryRun 时直接 return，**不产出任何报告** | 上线前无法离线验证配置 |

### 2.5 现存缺陷与风险（Defect）

| ID | 级别 | 问题 | 位置 | 建议 |
| --- | --- | --- | --- | --- |
| D-01 | 高 | `verifyUnloaded()` 超时即判定「输出容器已满」，随后 `closeOutput()` 走 `DROP_ITEM` **丢弃装备**。窗口延迟、网络抖动同样触发该路径 | `Worker:445-452, 477-482` | 超时先重试 N 次并复核容器槽位；丢弃需二次确认与计数上限 |
| D-02 | 高 | 空槽判定混用 `== null` 与 `!= Container.EMPTY_STACK`。`verifyGrindstonePreview` 认为非空才继续，若空槽返回 `null` 会误判「有输出」 | `Worker:313, 318, 398` | 统一封装 `isEmptySlot(stack)` |
| D-03 | 高 | `startXpKillAura()` 直接写全局 `CONFIG.client.extra.killAura.enabled = true`，该值会被持久化 | `Module:448` | 改用运行时开关 API；或退出时恢复原值 |
| D-04 | 中 | 失败后立即 `reset()` → 下一 tick 重新取件，无退避上限也无熔断；连续失败会持续消耗装备与书 | `Worker:145, 509` | 引入失败计数与指数退避（对应 G-03） |
| D-05 | 中 | `WAIT_CLOSE` 超时后仍强行进入后续状态，`beginOpen()` 检测到残留窗口直接 `fail("Unexpected open container")`，连带丢弃当前装备 | `Worker:146-149, 179-182` | 超时先强关窗口并确认 `openContainerId == 0` |
| D-06 | 中 | 双重操作延时：`submit()` 用 `operationDelayMs/50` 设 `actionDelayTicks`，`tick()` 又等一次 `operationDelayMs` | `Worker:87, 501-503` | 二选一，避免每动作 ~2×250ms |
| D-07 | 中 | `stations.get("anvil").getFirst()` 在无铁砧时抛 `IndexOutOfBoundsException`，被 `tick()` 兜底 `fail` 捕获，错误原因被掩盖 | `Worker:340, 413` | 取用前判空并给出明确状态 |
| D-08 | 中 | 书匹配要求 `STORED_ENCHANTMENTS` 恰好 1 条；多附魔书无法取用也无法识别为标记 | `Worker:564-572`, `Module:300-306` | 明确不支持并在扫描期告警，或支持多附魔书 |
| D-09 | 中 | `@Plugin(mixins = "dev.zenithproxy.autoenchant.mixin.**")` 但 `mixin` 包为空、JAR 内无 mixin 类 | `AutoEnchantPlugin:18` | 删除该声明，避免启动告警 |
| D-10 | 低 | 包名 `org.example` 与 `maven_group=dev.zenithproxy.autoenchant` 不一致；`BuildConstants` 在 `dev.zenithproxy.autoenchant` 包，源码跨包引用 | 全局 | 统一到 `dev.zenithproxy.autoenchant.*` |
| D-11 | 低 | 单 JAR 只声明 `mcVersions=[1.21.4]` 且只加载 `best-enchantments-1.21.4.json`，`1.21.11.json` 为 11 KB 死重（除非另建构建） | `build.gradle.kts`, `Catalog.load` | 明确多版本构建策略：分构建产出，或按服务端实际版本选择数据集 |
| D-12 | 低 | `preparePlan` CUSTOM 分支中 `leaves` 列表构建后未使用（死代码） | `Worker:232-243` | 清理 |
| D-13 | 低 | 每次 `scanNow()` 在 radius=16/vertical=8 下遍历 33×33×17 = 18513 个方块，每 100 tick 一次并逐方块 `World.getBlock` | `Module:154-168` | 分帧扫描或结果缓存，仅对变化区块重扫 |
| D-14 | 低 | `catalog` 与 `presets` 可变且无版本号，未来热重载会出现 worker 读到半更新状态 | `Catalog`, `Module` | 引入不可变快照 + `volatile` 引用切换 |

### 2.6 结论

代码已具备「**单件装备的完整闭环**」：取件 → 判定 → 祛魔 → 取书 → 逐步合并 → 校验 → 卸货，且服务端预览校验链路是扎实的（费用不入账不出结果、结果附魔逐项比对）。真正缺失的是**长跑运维所需的韧性**：铁砧补货（G-01）、错误分级与退避（G-02/G-03）、可观测性（G-11）、dry-run 验配置（G-10），以及若干会**误丢装备**的高危路径（D-01/D-02）。因此 v1.0 的定位应明确为「受控环境可用，生产环境需完成 P0 项」。

## 3. 需求范围

### 3.1 范围内

- 单 BOT、单工作区（一个附魔车间）的串行附魔作业；
- 铁砧合并 + 砂轮祛魔两条交互链路；
- 展示框标记 + 显式坐标两种绑定方式；
- PRESET（Wiki 预设）与 CUSTOM（自定义附魔集合）两种方案来源；
- 本体 KillAura 作为唯一经验来源；
- 成品/半成品/丢弃三种出货路径；
- 命令、配置、日志三类可运维接口。

### 3.2 范围外

- 不实现 XP 瓶投掷、红石经验机监控（`experienceSource` 固定 `KILLAURA`）；
- 不实现红石机器预处理（仅承认其为前置过滤，插件检测结果后自行决策）；
- 不实现多 BOT 协同、跨维度调度、跨代理集群；
- 不实现附魔书自动合成（书-书合并由方案表达式决定，非通用合成器）；
- 不修改服务端规则、不绕过「过于昂贵」上限；
- 不实现 GUI/Web 面板（仅 Discord/命令 embed）。

## 4. 功能需求

优先级定义：**P0** = v1.0 生产可用门槛；**P1** = 完整实现设计意图；**P2** = 增强项。

### FR-1 配置与校验

| 编号 | 需求 | 优先级 | 现状 |
| --- | --- | --- | --- |

| NFR-7 | 可维护性 | 新增预设 0 代码改动；新增装备槽位 0 代码改动 | 变更演练 |
| NFR-8 | 兼容性 | 产物字节码 Java 21；仅依赖 ZenithProxy 公开 API，不使用反射访问私有字段 | 构建 + 代码审计 |

### 6.2 预设数据集 Schema

```json
{
  "dataVersion": "1.21.4",
  "sourceUrl": "https://zh.minecraft.wiki/...",
  "sourceRevisionId": 1489816,
  "lastUpdated": "2026-09-25",
  "fetchedAt": "2026-09-28",
  "edition": "java",
  "notes": ["..."],
  "plans": {
    "<slot>": {
      "display": "头盔",
      "targetPlaceholder": "helmet",
      "variants": {
        "all": {
          "display": "全选（含荆棘）",
          "totalLevels": 45,
          "minXp": 753,
          "expression": "{[(helmet + thorns_3)@12 + (respiration_3 + unbreaking_3)@3]@11 + ...}@14"
        }
      }
    }
  },
  "conflicts": [["minecraft:protection", "minecraft:fire_protection", "..."]]
}
```

约束：
- `targetPlaceholder` 必须是 `BASE_ITEMS` 之一：`helmet|chestplate|leggings|boots|sword|axe|bow|crossbow|trident|mace|spear|pickaxe|shovel|hoe|fishing_rod|misc_item`；
- `totalLevels` 必须等于表达式所有 `@n` 之和（含 0 视为无注记，则跳过校验）；
- 表达式解析失败或含未知附魔/超等级叶子 → 该变体被**静默跳过**（建议改为告警，见 §12 Q-6）。

### 6.3 表达式语法（EBNF）

```
expression := term { "+" term }
term       := token [ "@" integer ] | "(" expression ")" [ "@" integer ]
            | "[" expression "]" [ "@" integer ] | "{" expression "}" [ "@" integer ]
token      := name [ "_" integer ]        (* 尾缀数字为附魔等级，默认 1 *)
```

语义：
- 每个 `Merge` 节点代表一次铁砧操作，`@n` 为指南标注的该次费用；
- 后序扁平化 = 执行顺序，不得重排合并树；
- `targetPlaceholder` 叶子代表装备本体（等级恒为 1），其余叶子代表附魔书；
- 三种括号在语义上等价，仅表示 Wiki 的原作者分组意图（便于对照原文）。

## 7. 状态机规格

### 7.1 阶段划分

| 阶段 | 状态 | 职责 |
| --- | --- | --- |
| 空闲 | `IDLE` | 检查前置（配置有效、铁砧在线、输入容器可解析）后开启事务 |
| 取件 | `OPEN_INPUT` → `WAIT_INPUT` → `TAKE_INPUT` → `VERIFY_INPUT` → `CLOSE_INPUT` | 打开输入箱、匹配目标、快照、Shift 取出、确认入包 |
| 祛魔 | `PREPARE_GRINDSTONE` → `OPEN_GRINDSTONE` → `WAIT_GRINDSTONE` → `GRIND_INSERT` → `GRIND_WAIT_RESULT` → `GRIND_TAKE` → `GRIND_VERIFY` → `CLOSE_GRINDSTONE` | 插入→等输出→取回→确认无附魔残留 |
| 备书 | `NEXT_BOOK` → `OPEN_BOOK` → `WAIT_BOOK` → `TAKE_BOOK` → `VERIFY_BOOK` → `CLOSE_BOOK` | 按需求顺序逐本取书，已持有时跳过 |
| 合并 | `OPEN_ANVIL` → `WAIT_ANVIL` → `PLACE_INPUTS` → `WAIT_PREVIEW` → (`CLOSE_FOR_XP` → `WAIT_XP` →)* → `TAKE_RESULT` → `VERIFY_RESULT` → `CLOSE_ANVIL` | 放料 → 预览校验 → 经验门槛 → 取结果 → 结果校验 |
| 出货 | `PREPARE_OUTPUT` → `OPEN_OUTPUT` → `WAIT_OUTPUT` → `UNLOAD_ITEM` → `VERIFY_UNLOAD` → `CLOSE_OUTPUT` | 成品/半成品卸货 |
| 失败 | `DROP_ITEM` → `BACKOFF` → `IDLE` | 丢弃事务物品后等待 `restartDelayMs` |
| 辅助 | `WAIT_CLOSE` | 等待窗口关闭确认 |

### 7.2 关键迁移条件（必须实现的行为约束）

1. `IDLE → OPEN_INPUT` 仅当：配置无错误 ∧ 存在已加载铁砧 ∧ 输入容器可解析 ∧ 当前无打开窗口。
2. `WAIT_PREVIEW → TAKE_RESULT` 仅当：结果槽非空 ∧ 费用可读 ∧ 附加魔与计划节点一致 ∧ 费用 ≤ 39 ∧ 等级达标。
3. `WAIT_PREVIEW → CLOSE_FOR_XP` 仅当：预览通过但等级不足；关闭窗口后进入 `WAIT_XP`，**不得**在窗口未关时唤起 KillAura。
4. 任一 `fail()` 后必须走出货/丢弃路径，不得直接回 `IDLE`（否则事务物品留在背包）。
5. `WAIT_CLOSE` 超时后**必须**确认 `openContainerId == 0` 才能进入下一打开动作（修 D-05）。
6. `BACKOFF` 结束必须 `reset()` 清空全部事务字段（目标、快照、操作序列、索引、槽位）。

### 7.3 事务字段不变量

`sourceSlot`、`playerSlot` ∈ [-1, 44]；`operationIndex ∈ [0, operations.size()]`；`bookIndex ∈ [0, books.size()]`；`itemSnapshot != null` 时 `target != null`。建议在 `reset()` 与每次迁移后以断言校验。

## 8. 关键算法要求

### 8.1 铁砧费用模型

```
cost_anvil = cost_enchant(left, right)
           + cost_sacrifice_penalty(right)      // 附魔书在牺牲槽有折扣
           + cost_repair_and_rename
           + prior_work_penalty 相关项
result_penalty = 2 * max(penalty(left), penalty(right)) + 1
survival_limit = 39   // 费用 > 39 时客户端显示「过于昂贵」，禁止取出
```

要求：
- `prior_work_penalty` 必须读取物品的 `minecraft:repair_cost` 组件；读取失败即判该件失败，**禁止假定为 0**，禁止从操作历史推算；
- 诅咒不是先前工作惩罚，不得按 `2^n - 1` 推导；
- 上述模型用于**开窗前的可行性预判**（对应 FR-3.7 / G-06），开窗后仍以服务端预览为准；
- 生存上限应配置化（当前硬编码 39）。

### 8.2 祛魔判定

```
if hasCurse(item):                   -> 半成品卸货（不尝试砂轮）
elif mode == PRESET:                 -> 有任何附魔即祛魔至白板
elif mode == CUSTOM:
    if policy == NEVER_GRINDSTONE:   -> 保留现有附魔
    if policy == ALWAYS_GRINDSTONE:  -> 祛魔
    else:  // SMART
        if 目标集合内部冲突:                       -> 祛魔
        if 现有附魔与目标存在互斥:                  -> 祛魔
        if 直接追加费用 > 上限:                    -> 祛魔
        if 直接追加费用 - 祛魔重做费用 >= threshold: -> 祛魔
        else:                                       -> 保留
```

要求：祛魔后**重新读取**物品附魔与惩罚，不得沿用祛魔前的预估。

### 8.3 合并结果校验

- 期望附魔集合由计划节点递归求得：`merge = max(l, r) + (l == r ? 1 : 0)`，且需按该附魔 `maxLevel` 截断；
- 实际集合按槽位类型读取：装备读 `ENCHANTMENTS`，书读 `STORED_ENCHANTMENTS`；
- 比较须为**严格相等**（不多不少），否则终止该件；
- 书匹配要求单附魔且等级精确（当前实现），多附魔书需明确为不支持并告警（D-08）。

### 8.4 目标匹配与身份

`targetFor(item)` 按物品注册名精确匹配；`sameStackIdentity(a, b)` = 同 id ∧ 同附魔集合 ∧ 同惩罚。要求永远用「快照比对」而非「槽位记忆」确认事务物品，避免玩家移动导致误操作。

## 10. 验收标准

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| AC-1 | 空场景启动 | 无容器、无铁砧、无标记时插件不报错，`status` 给出明确等待原因，不发起任何交互 |

| AC-9 | 结果不符 | 人为使预览结果与计划不一致，插件终止该件，不消耗结果 |
| AC-10 | 容器满 | 输出与半成品均满时，按策略有限次重试后丢弃本事务物品，日志明确，不丢玩家其他物品 |
| AC-11 | 断线恢复 | 事务中途断线重连，不重复点击、不重复消耗书、不误判成功；环境可操作后续跑 |

| AC-14 | 长跑 | 8 小时连续运行无卡死、无内存增长异常、无未处理异常刷屏 |

## 附录 B：标记布置速查

| 展示框内物品 | 角色 | 容器定位方式 |
| --- | --- | --- |
| 红石粉 | `input` 待附魔装备 | 展示框附着方块 |
| 红石块 | `output` 成品 | 展示框附着方块 |
| 铁砧（物品） | `anvil_supply` 铁砧补给 | 展示框附着方块 |
| 附魔书 / 铁砧补给 | `book:<附魔>:<等级>`、`anvil_supply` | 展示框下方第一个容器（深度 ≤ `supplyScanDepth`） |
| 灰色染料（可配） | `semi_finished` 半成品/隔离 | 展示框附着方块 |

同一角色只能有**一个**有效绑定；多绑定时当前实现静默返回「不可用」，需按 FR-2.7 改为显式告警。
