# AutoEnchant 重构方案（基于当前工作区改动 + VillagerTrader 架构）

> 本文只做分析与方案，**没有改动任何现有代码**。所有行号取自当前工作区（未提交状态）。

## 0. 结论先说

1. **KillAura 可以开**：字段名是 `CONFIG.client.extra.killAura.enabled`（注意是 `killAura` 驼峰，不是 `killaura`），配合 `MODULE.get(KillAura.class).syncEnabledFromConfig()` 生效。现有代码这两步都已经写对了，问题只在“什么时候开/什么时候还”。
2. 你这次改的方向是对的（配置从 `List<Job>` 收敛成 `LinkedHashMap<String, Enchant>`、状态机搬进 Module、引入 `EquipmentType`、引入 `postEnchantStoreMode`），但它是一件**做了一半的手术**：配置模型换了，剩下 5 个文件还在用旧模型，所以现在**编译不过**（5 处硬语法错误 + 44 处 `AutoEnchantConfig.Job` 引用 + 一批已删除字段的引用）。
3. 建议的落地顺序不是“先修语法再想架构”，而是**先定稿配置模型（唯一事实来源）→ 再一次性把 Module/Worker/Command/Validator 对齐**，否则会反复返工。本文给出定稿 schema、状态机映射表、文件拆分清单和分阶段验收标准。

- `Enchant.getRenameName()` 返回 `ItemData`，而 `renameName` 是自由文本显示名 —— 逻辑上不成立，应删。

## 2. 目标架构

照 trader 的**“配置即事实来源 + Module 单状态机”**模型，但把 trader 单文件 2700 行的教训吸收掉：**Module 只做状态机骨架，能力按职责拆成协作类**。

```
org.example
├── AutoEnchantPlugin.java            注册 config（三参，挂 serializer）+ module + command
├── config/
│   ├── AutoEnchantConfig.java        纯数据 + 少量派生方法（~150 行）
│   ├── AutoEnchantConfigSerializer.java  旧格式迁移（现有，扩展 enchants 迁移）
│   └── EnchantJobIterator.java       enabled&complete 的 job 数组 + select()（~60 行）
├── data/
│   ├── EnchantPresetCatalog.java     （不动）
│   ├── CustomEnchantPlanner.java     （不动）
│   ├── EnchantExpressionParser.java  （不动）
│   └── EquipmentTypes.java           新增：ItemData/ItemStack → EquipmentType（~120 行）
├── module/
│   ├── AutoEnchantModule.java        生命周期、事件、tick→switch(state)、对外 status（~380 行）
│   ├── EnchantStationScanner.java    扫描铁砧/砂轮/展示框、解析容器、导入模板（~460 行）
│   ├── EnchantXpFarm.java            killSpot 寻路 + KillAura 借用/归还 + 监控（~230 行）
│   └── EnchantSequence.java          原 worker 的状态迁移（~700 行，替换 EnchantWorkflowWorker）
│   └── （删除）EnchantWorkflowWorker.java
├── util/
│   ├── ContainerOps.java             开/关容器、awaitContainerClosed、settle、Click 宏（~220 行）
│   ├── InventoryOps.java             找物品/找空位/数书本/产物匹配（~200 行）
│   └── ItemIdentity.java             身份 key、同名同词条判定、诅咒判定（~80 行）
└── command/AutoEnchantCommand.java   按 job id 的命令树（~700 行）
```

拆分原则：

- **状态迁移只写状态，不写“怎么点”**：动作全部走 `ContainerOps` / `InventoryOps`，这样状态代码可以一眼读成流程。
- **扫描与执行彻底解耦**：扫描只产出 `ScanResult`（stations / markers / jobFrames / problems）并写 config；执行只读 config + 缓存。现在 `scanNow()` 里同时干了“发现、校验、写盘、打日志、统计”，是 Module 膨胀的主因。
- **两套状态机合并为一套**：保留你的 `AutoEnchantModule.State`（trader 风格），删掉 worker 的 `Origin/State` 私有枚举；worker 里需要的 `CLOSE_*` / `WAIT_*` 用 `awaitContainerClosed()` 收敛（见 §4）。

### 3.2 必须修的三处

| 项 | 现状 | 建议 |
| --- | --- | --- |
| `itemEnchantments` | `Object2IntLinkedOpenHashMap<Enchantment>` | 改 `Object2IntLinkedOpenHashMap<String>`（id → level）。`Enchantment` POJO 删除；`Mode.CUSTOM` 不再需要 `List<Enchant>` 与 map 双表示，统一成有序 map，命令 `add` 就是 `put`（天然去重 + 保序），`clear`/`del`/`list` 直接映射 |
| `containerPositions` | `Map<String,String>`，0 使用 | 删掉。角色坐标已经有显式字段；真要留多角色绑定，用 `Map<ContainerRole, BlockPos>` 且 `ContainerRole` 用枚举（`INPUT/OUTPUT/OVERFLOW/ANVIL_SUPPLY/GRINDSTONE_SUPPLY/SEMI_FINISHED`），不要字符串 |
| `GrindstoneChest` | 大写开头 | `grindstoneChest`（Gson 字段名就是 JSON key，大写会很别扭） |

### 3.3 兼容旧配置（serializer 扩展）

`AutoEnchantConfigSerializer.normalize()` 目前只处理坐标字符串。补两条：

1. `jobs[]` / `targets[]` → `enchants{}`：以 `enchantItem` 短名（去 `minecraft:`，冲突时加 `_2`）为 key；`enchantments` 数组 → `itemEnchantments` map；`semiFinishedChest` → `postJobStoreMode=TO_OVERFLOW` + `overflowChestPos`。
2. 站点级旧 `outputChest`/`semiFinishedChest` → 分别落到**每个** job 的 `outputChest` / `overflowChestPos`（一次性拷贝，之后各 job 独立）。
3. 加 `configVersion`（当前设为 2），后续迁移可按版本分支，不再靠“字段存不存在”猜。

> 别忘了 `AutoEnchantPlugin` 换成三参 `registerConfig(name, class, AutoEnchantConfigSerializer.INSTANCE)`，否则以上全部不生效且旧配置会导致启动退出。

## 4. 状态机重构

### 4.1 与你现有 State 枚举的对齐

| 你的状态 | 建议 | 说明 |
| --- | --- | --- |
| `ENTRYPOINT` | 保留 | tick 入口：选下一个 job，`EVAL_RESTOCK` |
| `EVAL_RESTOCK` | 保留 | 判断背包是否有该 job 的装备（续做）→ 没有则 `RESTOCK_INPUT_GO_TO_CHEST` |
| `RESTOCK_INPUT_GO_TO_CHEST / WITHDRAW / AWAIT_WITHDRAW` | 保留 | 从 `inputItemChest` 取一件 |
| `EVAL_UNCHANT` | 保留并明确语义 | “是否需要砂轮祛魔”：`mode=PRESET` 且已有词条 → 需要；`CUSTOM` 走杂质策略；空词条 → 跳过 |
| `RESTOCK_ANVIL_GO_TO_CHEST / WITHDRAW / AWAIT_WITHDRAW` | 保留 | 铁砧补给 |
| `CRAFT_ANVIL_BLOCKS / AWAIT_CRAFT_ANVIL_BLOCKS` | 保留 | 铁块→铁砧（对应 trader 的 `CRAFT_EMERALD_BLOCKS`） |
| `RESTOCK_ENCHANTED_BOOK_GO_TO_CHEST` | **补上 GO_TO** | 现在缺失，`RESTOCK_ENCHANTED_BOOK__AWAIT_WITHDRAW` 还是双下划线 |
| `ENCHANT_INTERACT_WITH_ANVIL / AWAIT_...` | 保留 | 右击铁砧 |
| `ENCHANT_TRY_START` | 保留 | 放置左/右输入 + 改名 |
| `AWAIT_ENCHANT` | 保留 | 校验预览 + 费用 + 取结果 |
| `STORE_GO_TO_CHEST / DEPOSIT / AWAIT_DEPOSIT` | 保留 | 中间卸货（背包满） |
| `READY_NEXT_ENCHANT` / `NEXT_ENCHANT` | 合并语义 | `NEXT_ENCHANT` = 还有合并步骤 → 回 `ENCHANT_INTERACT_WITH_ANVIL`；`READY_NEXT_ENCHANT` = 当前装备做完 → `POST_ENCHANT` |
| `POST_ENCHANT` / `POST_ENCHANT_INPUT_*` | 保留 | 按 `postEnchantStoreMode` 卸货 |
| `POST_ENCHANT_OVERFLOW_*` | 保留 | `overflowChestPos` |
| `AWAIT_RESTOCK` | 保留 | 空箱/退避（替代现在的 `emptyChestStreak` + `restartDelayMs`） |

**删掉的状态**：worker 里的 `WAIT_CLOSE` / `CLOSE_*` 全部不要。trader 的做法是每个状态开头 `if (!awaitContainerClosed()) return;`，关闭只是“等一下”，不是一个状态；一个 `CloseContainer` 请求就能覆盖，状态数直接砍掉 6~8 个。

### 4.2 通用骨架（照 trader，但抽成类）

```java
private void onTick(ClientBotTick event) {
    if (!PLUGIN_CONFIG.enabled) return;
    if (!CACHE.getPlayerCache().getThePlayer().isAlive()) { reset(); return; }
    switch (state) {
        case ENTRYPOINT -> {
            if (!jobIterator.hasNext()) return;      // 无 job：状态文案 + 返回，不空转
            setState(State.EVAL_RESTOCK);
        }
        case EVAL_RESTOCK -> { ... }
        case RESTOCK_INPUT_GO_TO_CHEST -> {
            pathFuture = BARITONE.rightClickBlock(chest.x(), chest.y(), chest.z());
            pathFuture.addExecutedListener(f -> waitForInteractTimer.reset());
            setState(State.RESTOCK_INPUT_WITHDRAW);
        }
        ...
    }
}
```

配套三件套（都要从 worker 里提出来）：

| 组件 | 来源 | 作用 |
| --- | --- | --- |
| `ContainerOps.awaitContainerClosed()` | trader 同名方法 | 关箱后等 id0 解冻，替代 `WAIT_CLOSE` 状态 |
| `InventoryActionMacros.withdraw(...)` | 代理自带 | 取货宏，替代手写 `ShiftClick` 逐槽判断 |
| `EnchantJobIterator` | trader `TradeIterator` | `enabled && complete` 的 job 数组 + `select()`，替代 `runnableJobs` 缓存 + `inputCursor` |

### 4.3 事务字段不变量（保持不变，但要集中）

`EnchantSequence` 单例字段保持不变语义：`activeJob`、`itemSnapshot`、`operations`、`books`、`operationIndex`、`bookIndex`、`playerSlot`、`sourceSlot`、`activeContainerId`、`waitingCost`、`anvilPosition`。规则：

- 所有状态迁移必须走 `setState()`（带 `debug` 日志），禁止裸赋值 —— 现在 worker 里 60+ 处 `state = ...` 裸赋值，出问题只能靠 `debugSnapshot()` 反推。
- `itemSnapshot` 只在四个地方变：取货、祛魔完成、改名完成、取走产物。其它任何状态不得动它。
- 失败只走 `fail(reason)` → `POST_ENCHANT`，不再各状态自己拼“下一步”。

## 6. KillAura / 经验来源

### 6.1 能不能开

可以，且现有写法正确：

```java
KillAura killAura = MODULE.get(KillAura.class);       // com.zenith.module.impl.KillAura
CONFIG.client.extra.killAura.enabled = true;          // 注意 killAura 驼峰
killAura.syncEnabledFromConfig();
```

`KillAura.isEnabled()` 的实现就是读 `CONFIG.client.extra.killAura.enabled`，所以改 config + sync 是唯一正路；不要直接 `killAura.enable()`（会绕开配置持久化）。

三条安全线（现有代码已有，重构时要保留）：

1. **只归还自己开的**：`ownsKillAuraActivation` 标记，`stopXpKillAuraIfOwned()` 才关。
2. **交互期间不开**：进入 `ENCHANT_INTERACT_WITH_ANVIL` 前必须 `stopXpKillAuraIfOwned()`，否则开箱/点击会被攻击动作打断。
3. **中断条件**：死亡、血量 < `minimumHealth`、维度变化、`killAuraMaxSeconds` 超时、`noXpTimeoutMs` 无经验进度、传送 > 16 格、寻路 3 次失败。

### 6.2 `experienceSource` 语义（需要你确认）

| 值 | 建议语义 | 待确认 |
| --- | --- | --- |
| `NONE` | 不主动刷经验：等级不够就 `AWAIT_RESTOCK` 退避，并周期性提示 | — |
| `KILL` | 走到 `killSpot` → 开 KillAura → 等级够了关掉继续附魔（= 现在的行为） | — |
| `EXP` | **两种可能**：(a) 站在 `killSpot` 不攻击，只吸经验球/等刷怪笼产出；(b) 从 `anvilChest`/专门容器取经验瓶投掷 | 请你定一下，我按 (a) 实现更省事，且与 `experienceSource.NONE` 区分度足够 |

另外 `Validator` 现在写的是 `!"KILLAURA".equalsIgnoreCase(config.experienceSource)`，字段已是枚举，要改成 `config.experienceSource == ExperienceSource.NONE` 之类的枚举校验。

## 7. `EquipmentType` 怎么落地

现在只有枚举没有服务，扫描仍然用 `MAX_DAMAGE` 判断“这是不是装备”。建议：

```java
public final class EquipmentTypes {
    public static EquipmentType of(ItemData data);   // name/tag 推断，未知返回 NONE
    public static boolean isEnchantable(ItemData data); // != NONE
}
```

用途（按收益排序）：

1. **展示框分类**：`jobFrame()` 里 `EquipmentType.NONE` 直接不出作业，比 `MAX_DAMAGE` 更贴近业务（弓/三叉戟/盾也有耐久，但不是“要附魔的近战套”）。
2. **命令展示**：`list` 显示 `[SWORD] diamond_sword`，一眼看出作业归类。
3. **未来多类型取货**：同一取货箱混装时按类型过滤，避免把斧头当剑取。
4. **持久化**：`getId()/from(int)` 保留，供以后把“装备类型”写进 config 做精确匹配。

注意 `1.21.4` 是否存在 `SPEAR`（你的枚举里有，`MACE` 也有）—— 落地前用 `ItemRegistry` 校验一遍，查不到的给 `NONE` 兜底即可，不要抛异常。

## 10. 需要你拍板的问题

1. **`GrindstoneChest` 到底指什么？** 我按“砂轮补给箱（对应 `anvilChest`）”理解。如果它其实是“半成品/失败品箱”，那 `postEnchantStoreMode` 和它的关系要重新设计。
2. **失败品去哪？** 现在 `postEnchantStoreMode` 只描述“成功卸货”。失败（祛魔不匹配、无合并顺序、书不够）建议固定走 `TO_OVERFLOW`，还是单独保留一个 `semiFinished` 角色？
3. **`containerPositions` 保留吗？** 建议删（与显式字段重复，且是 `String` 坐标）。
4. **`experienceSource = EXP` 的语义**（见 §6.2）。
5. **`renameOrder` 保留吗？** 建议保留字段 + 命令（改名挂在首次合并上只花 1 级，挂最后一次可能多花 15 级，这个开关有实际价值）。
6. **`add` 是否仍允许省略坐标**（缺省时用 `scan` 从展示框下方解析）？建议允许，但要在 embed 里明确写“坐标来自扫描，不是手填”。
